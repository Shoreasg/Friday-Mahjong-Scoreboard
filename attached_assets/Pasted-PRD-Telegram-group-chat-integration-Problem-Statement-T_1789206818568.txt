PRD: Telegram group chat integration
Problem Statement
The friend group records every Friday Mahjong session on the scoreboard, but the group's actual conversation lives in a Telegram group chat. That split costs the group three things:

Results don't reach people. When an admin records a session, nothing happens anywhere the group is actually looking. Someone has to remember to open the site, or an admin has to manually retype the result into the chat. In practice the week's winner, settlement amount, and the Zha Hu (诈胡) / 谢谢开相 (Kai Xiang) tallies get announced inconsistently or not at all.
Organising a game is manual and lossy. Getting four players together means someone typing "mahjong this friday?" into the chat and then scrolling back through replies to work out who actually said yes. There is no structured way to ask, and no tally.
Answering simple questions means leaving the chat. "Who won last week?", "how much am I down overall?", "how many times has he Zha Hu'd?" are all answerable from the scoreboard, but only by switching apps. The data is public and already computed — it's just not where the conversation is.
The underlying problem is that the scoreboard is a system of record with no voice in the place the group congregates.

Solution
A Telegram bot lives in the group chat and closes the loop in both directions.

It announces. When an admin records a Mahjong session, the bot immediately posts the result to the group — date, winner, each player's ending balance and net position against the $500 starting balance, rounds played, the Zha Hu and 谢谢开相 counts, any notes, and a link back to the scoreboard. Nobody has to remember to do anything.

It lets admins speak through it. The admin dashboard gains a Telegram card with a free-text composer that posts a message to the group as the bot, and two one-tap buttons that start a native Telegram attendance poll — "Mahjong tonight?" and "Mahjong this Friday?" — with Yes / No / Maybe options. Because the poll is non-anonymous, Telegram itself shows the running tally and the names of who voted, right in the chat.

It answers questions. Group members can type /last for the most recent session's result, /standings for the net winnings leaderboard and win counts, and /help to see what the bot can do. Every number it reports is already publicly readable on the site, so the bot exposes nothing new — it just puts the answer where the question was asked.

The feature is designed to fail quietly and honestly. If Telegram is unreachable when a session is saved, the session is still saved — the admin is told the announcement failed and can re-post it with the broadcast composer. If the bot isn't configured at all, the app runs exactly as it does today.

User Stories
Announcing results
As a group member, I want the bot to post the result as soon as an admin records a session, so that I learn the outcome without opening the scoreboard.
As a group member, I want the announcement to name the winner prominently, so that I can see at a glance who took the week.
As a group member, I want to see every player's ending balance in the announcement, so that I know exactly where I finished.
As a group member, I want to see each player's net position against the $500 starting balance, so that I know whether I was up or down without doing arithmetic.
As a group member, I want the announcement to include rounds played and the settlement amount, so that I have the full shape of the session.
As a group member, I want the Zha Hu (诈胡) and 谢谢开相 counts in the announcement, so that the house-rule running jokes stay alive in the chat.
As a group member, I want any notes the admin recorded to appear in the announcement, so that context about the session isn't lost.
As a group member, I want the announcement to link to the scoreboard, so that I can jump to the full history and analytics if I want more.
As an admin, I want the announcement to fire automatically on save, so that announcing is not one more thing I have to remember.
As an admin, I want a session to be saved even when Telegram is down, so that a third-party outage never blocks me from recording our game.
As an admin, I want to be told clearly when an announcement failed to send, so that I know the group didn't get it and can act.
As an admin, I want a failed announcement to be re-sendable by hand, so that a transient Telegram failure doesn't permanently lose the post.
As an admin, I want a player whose name contains punctuation or angle brackets to not break the announcement, so that an unusual nickname never silently kills our notifications.
Broadcasting
As an admin, I want to type a message in the dashboard and have the bot post it to the group, so that I can make announcements without switching apps.
As an admin, I want to see exactly what will be sent before it goes out, so that I don't publish a typo to everyone's phone.
As an admin, I want to confirm before sending, so that a misclick doesn't post to the group.
As an admin, I want to see how much of the message length budget I've used, so that I don't compose something Telegram will reject.
As an admin, I want to type any characters I like — brackets, asterisks, emoji — without the message being rejected, so that the composer never surprises me with a formatting error.
As an admin, I want to be told when a broadcast fails, so that I don't assume the group received something they didn't.
Attendance polls
As an admin, I want to start a "Mahjong tonight?" poll with one tap, so that organising a game takes seconds.
As an admin, I want to start a "Mahjong this Friday?" poll with one tap, so that I can plan ahead as well as same-day.
As a group member, I want to answer Yes, No, or Maybe, so that I can signal a tentative availability rather than being forced into a binary.
As a group member, I want to see who has voted and how, so that I know whether we have four players before committing my evening.
As a group member, I want to vote inside Telegram with one tap, so that RSVPing doesn't require an account, a link, or a browser.
As an admin, I want to confirm before starting a poll, so that I don't spam the group with duplicate polls by accident.
Bot commands
As a group member, I want to type /last and get the most recent session's result, so that I can settle an argument about who won without leaving the chat.
As a group member, I want to type /standings and get the net winnings leaderboard and win counts, so that I can see where I sit overall.
As a group member, I want to type /help and see what the bot can do, so that I can discover the commands without being told.
As a group member, I want the bot to respond only to commands aimed at it, so that it doesn't read or react to our ordinary conversation.
As a group member, I want an unrecognised command to be ignored rather than answered with noise, so that the bot never clutters the chat.
Safety, privacy and abuse
As a maintainer, I want the bot to ignore any chat other than our configured group, so that a stranger who finds the bot cannot use it.
As a maintainer, I want inbound requests that aren't genuinely from Telegram to be rejected, so that the public endpoint can't be driven by anyone who guesses the URL.
As a maintainer, I want the bot to only ever expose data that is already public on the site, so that the integration introduces no new disclosure risk.
As a maintainer, I want a malformed or unexpected inbound update to never crash the handler or trigger an endless retry loop, so that one bad message can't take out the endpoint.
Operating and developing
As a maintainer, I want the server to start normally when no bot credentials are configured, so that the Telegram feature is optional and local development needs no secrets.
As a contributor, I want to run the stack locally without a bot token or fake placeholder credentials, so that getting started stays as simple as it is today.
As a maintainer, I want a single command to register the bot's webhook, so that wiring it up after a deploy is not a hand-typed HTTP call with a secret in my shell history.
As a maintainer, I want a single command to inspect the webhook's current state and last error, so that when commands mysteriously stop working I have somewhere to look.
As a maintainer, I want a clear log line at startup telling me whether the integration is configured, so that "the bot isn't posting" is never a mystery.
As a maintainer, I want failures to send to be logged with enough context to diagnose them, so that silent failures are still recoverable after the fact.
As a maintainer, I want the bot token and chat ID to live in environment configuration, so that rotating credentials never requires a code change.
As a maintainer, I want to be warned if our group is upgraded to a supergroup and its chat ID changes, so that announcements failing silently is not the way I find out.
Implementation Decisions
Scope
In scope: announce-on-record, admin ad-hoc broadcast, admin-triggered attendance polls, and read-only bot commands.
Deliberately not built: scheduled or automatic reminders. Polls are always admin-initiated. This is the decision that keeps the feature free of any scheduler, which matters because the deployment target is Replit autoscale — instances scale to zero and no long-lived process is guaranteed.
Module boundaries
A new domain-agnostic workspace package, @workspace/integrations-telegram, owns the transport: sending a message, sending a poll, verifying the webhook secret, and parsing inbound updates. It knows nothing about Mahjong.
Mahjong-specific message templates, the command router, and the webhook handler live in the API server alongside the other route logic.
This mirrors the existing split, where the Gemini integration package exposes a generic client and the Mahjong-specific prompt lives in the API server's route. Putting templates in the integration package would invert the dependency direction, because templates need domain types and the starting-balance rule.
The transport package must remain a dumb adapter — URL construction, the HTTP call, and error mapping only. No branching, no formatting, no retry logic. This is a load-bearing constraint: it is what allows the whole feature to be tested through a single seam (see Testing Decisions).
Configuration
Three environment values: a bot token, a target chat ID, and a webhook secret token.
Configuration is read lazily, at call time. A missing token must never throw at import.
When unconfigured, the feature disables itself cleanly: announcements are skipped with a warning, the admin endpoints return a "not configured" service-unavailable response, the webhook acknowledges and ignores, and the server logs one explicit line at startup.
This is a deliberate departure from the existing Gemini integration, which validates at module scope and throws. That pattern already forces fake placeholder credentials into the example environment file just to let the server boot. Repeating it here would be worse, because the announce path runs inside the session-create route, so every test run, CI job, and local Docker Compose start would need a bot token.
Chat targeting
A single configured chat ID, supplied as an environment value. No registry table.
The webhook detects Telegram's chat-migration signal and logs an actionable error, because a group upgraded to a supergroup gets a new chat ID and every send would otherwise begin failing silently.
Announce-on-record semantics
Only session creation announces. Edits and deletions are silent; corrections go out through the broadcast composer.
The send is awaited with a short timeout, but never blocks or reverses the save. The session is always persisted and the create response reports the announcement outcome, which the dashboard surfaces as a non-blocking warning.
Fire-and-forget was explicitly rejected: on autoscale, work started after the response is flushed can be frozen or reclaimed, so a detached send can silently never happen.
A transactional outbox was explicitly rejected: it is the textbook answer, but autoscale provides no background worker to drain it, so it would require either opportunistic draining or an external scheduler — reintroducing exactly the infrastructure this design avoids. The broadcast composer serves as the manual retry path instead.
Message formatting
Templated messages (announcements) are sent with Telegram's HTML parse mode, and every interpolated value passes through a single escaping helper.
This is a correctness requirement, not a stylistic one: player names are admin-entered free text. Sent unescaped under a parse mode, a name containing < or an unbalanced entity causes Telegram to reject the entire message, so one oddly named player would silently break all announcements.
HTML was chosen over MarkdownV2 specifically because it requires escaping only three characters, whereas MarkdownV2 requires escaping eighteen — including . and -, which appear in every date and every negative balance.
Admin broadcasts are sent with no parse mode at all, so arbitrary typed text can never produce a formatting rejection.
Polls
Native Telegram polls, non-anonymous, with Yes / No / Maybe options and two preset questions.
Results are not ingested or stored. Because the poll is non-anonymous, Telegram displays the live tally and voter names in the chat, which is the entire user need. Ingesting votes would require storing poll identity, handling vote changes and retractions, and building a display surface — to reproduce information the group can already see.
Inbound webhook
A single webhook endpoint on the existing API server. Long-polling is impossible on autoscale, and a second always-on deployment was rejected as unjustified cost for this workload.
Authenticity is established by Telegram's secret-token header. A request with a missing or incorrect secret is rejected outright, since by definition it did not come from Telegram.
Authorisation is the chat ID. Any update from a chat other than the configured one is dropped and acknowledged. Within the group, permissions are flat — no Telegram-user allowlist and no registration command — because every value a command can report is already publicly readable on the site. The control being enforced is scope and abuse, not confidentiality.
The bot's group privacy mode stays enabled, so it receives only commands addressed to it, replies, and mentions — never the group's ordinary conversation.
Webhook robustness
The endpoint acknowledges successfully for every authentic update — success, unknown command, malformed payload, or handler exception — and logs failures server-side.
This is driven by two Telegram behaviours: a non-success response causes the same update to be retried repeatedly, turning one malformed update into a poison pill that blocks the queue behind it; and a slow response causes redelivery, which autoscale cold starts make likely.
Duplicate deliveries are accepted rather than de-duplicated. No processed-update table. Every command is read-only, so the worst case is a reply posted twice.
The accepted cost is stated plainly: a genuine handler bug is invisible to users, because the bot simply does nothing. Logging is therefore the only signal and must be deliberate.
Commands
/help, /last, and /standings ship in v1.
Each is a projection of the aggregation the session-summary endpoint already computes — totals, latest session, winner counts, Zha Hu counts, 谢谢开相 counts, and per-player net winnings.
The command set is kept small on purpose: commands registered with Telegram appear in the bot's menu permanently and become a standing contract.
Implied refactor: the summary aggregation currently lives inline inside the summary route handler. It must be extracted into a shared function that both the HTTP route and the command formatters call. This is the only change to existing behaviour-bearing code the feature requires, and duplicating the aggregation instead is explicitly rejected.
API contract
The two admin operations — broadcast and start-poll — are added to the OpenAPI specification and get generated client hooks and validation schemas. The session-create response schema gains a field reporting the announcement outcome.
The webhook is deliberately excluded from the OpenAPI specification. Its only client is Telegram, which will never consume the spec, and code generation would emit a browser-side mutation hook for an endpoint the browser must never call. Its payload is validated by a hand-written schema inside the transport package, parsing only the fields actually read.
Regenerating the API client and schemas after editing the specification is a required step, per the repository's existing convention.
Admin UI
A Telegram card on the existing admin dashboard, behind the same admin gate already in place: a composer with a live character count against Telegram's message limit, and two poll preset buttons.
Every action confirms through a dialog that previews the exact text to be sent. The justification is that sending is irreversible and public — unlike every other admin action, which is privately correctable — and a bot can only delete its own messages for a limited window.
Delivery
Three independently shippable increments, in this order:

Transport package, lazy configuration, announce-on-record, tests, and architecture diagram update.
Admin broadcast and poll: OpenAPI additions, code generation, and the dashboard card.
Inbound webhook, the three commands, the summary-aggregation extraction, and the webhook registration/inspection tooling.
The ordering is deliberate: increment 1 proves the credentials and chat targeting end-to-end with the smallest blast radius, and the public endpoint lands last, only after outbound sending is known to work.

Testing Decisions
What makes a good test here
Tests assert on externally observable behaviour — the HTTP status and body the API returns, and what the application asked Telegram to send. They do not assert on internal call ordering, private helpers, or module structure. A test should survive any refactor that preserves what a user or the Telegram API would observe.

The seam
One seam, at the application's HTTP boundary. The existing API server test suite already boots the real application on an ephemeral port and drives it with genuine HTTP requests, mocking the database and the auth provider at the module level. The Telegram feature adds exactly one more mocked module — the transport package — and is otherwise tested the same way.

A lower seam that intercepts outbound HTTP was considered and rejected on evidence: the existing harness issues its own requests to the application using the same global HTTP primitive, so stubbing that primitive would sabotage the test harness itself.

The single-seam approach is what the "dumb transport" constraint buys. All logic worth testing — escaping, templates, command routing, authorisation, the unconfigured state, failure semantics — sits above the seam and is reachable through the existing harness. If logic is ever allowed to drift down into the transport, a second seam becomes unavoidable.

What gets tested
Through the HTTP seam:

Creating a session sends an announcement containing the winner, balances, net positions, rounds, house-rule counts, and notes.
Creating a session still succeeds, and still returns its normal success status, when the transport throws.
The create response reports the announcement outcome accurately in both the success and failure cases.
A player name containing characters that are significant in the chosen parse mode is escaped rather than passed through.
Nothing is sent, and no error is raised, when the integration is unconfigured; the admin endpoints report unavailability instead.
The broadcast and poll endpoints reject signed-out and non-admin callers, consistent with the existing admin-gated routes.
The broadcast endpoint rejects a message exceeding Telegram's length limit.
The webhook rejects a request with a missing or wrong secret token.
The webhook ignores an update originating from a chat other than the configured one.
The webhook acknowledges — and sends nothing — for an unknown command, a malformed payload, and a handler that throws.
Each of the three commands produces a reply containing the expected figures.
Prior art
The API server's existing session route tests are the direct model: hoisted module mocks for the database and auth provider, the real application booted over an ephemeral port, and assertions on response status and body. New tests follow that file's structure and helpers.

Client-side testing
No new client test seam. The web application's only existing test covers pure data-shaping functions using the Node built-in test runner, and the package has no test runner wired into its scripts. The dashboard card is therefore kept deliberately logic-free — a form, a generated mutation hook, and a confirmation dialog. Should non-trivial logic appear, it is extracted as a pure function and tested in the style of the existing pure-function test.

Out of Scope
Scheduled or automatic reminders. All polls and broadcasts are admin-initiated. Nothing in this feature runs on a timer.
Ingesting poll results. Votes stay in Telegram; the application never reads, stores, or displays them, and there is no attendance data in the database.
Announcing session edits and deletions. Only creation announces. Corrections are manual, via the broadcast composer.
Editing or deleting previously sent messages, and the message-identifier storage that would require.
Multiple group chats. One configured chat. No registry, no per-chat settings, no fan-out.
A delivery outbox, retry queue, or background worker. Failed sends are surfaced to the admin and re-sent by hand.
Update de-duplication. Duplicate deliveries are tolerated.
Any command that mutates data. Recording, editing, and deleting sessions remain web-only and admin-only. The bot is read-only.
A Telegram-user-to-admin mapping or privileged in-chat commands. Administration happens in the web application.
Direct messages, per-player notifications, or mentions of individual users.
Rich media — no images, no chip-scan photos, no charts posted to the chat.
Localisation of bot output.
Component or end-to-end tests for the dashboard card.
Further Notes
Supergroup migration is the most likely silent failure. If the group is ever upgraded to a supergroup, Telegram issues a new chat ID and every send begins failing. The design handles this by detecting the migration signal and logging an actionable error rather than by building a registry — but whoever operates this should know that the fix is to update the configured chat ID.
An unregistered or stale webhook produces no error anywhere. Commands simply do nothing, because the request never arrives. Telegram's webhook-info call reports the last delivery error and is the single most useful diagnostic this feature has; the inspection command exists specifically so that signal is one command away.
The repository's architecture-diagram hook will block commits for this work. The feature necessarily touches both the route index and the OpenAPI specification, which are on the hook's watched-path list, so the interactive architecture diagram source must be updated in the same commit. The new transport package's client should also be added to that watched-path list, mirroring the entry that already exists for the Gemini integration client.
Code generation is a required step in increment 2. Editing the API specification without regenerating the client and schemas will leave the dashboard card unable to call the new endpoints.
Telegram enforces rate limits on group messages. The expected volume — roughly one announcement a week plus occasional admin actions — sits far below any threshold, so no client-side rate limiting is built. A rate-limit rejection is treated like any other send failure: reported, not retried in-request.
Message length is capped by Telegram. The broadcast composer enforces the limit before sending, and announcement templates should be written with the cap in mind, though a four-player session cannot realistically approach it.
Local development of inbound commands requires a tunnel. Telegram cannot reach a local machine, so testing commands against a real bot needs a public tunnel or a manually forwarded payload. The existing Docker Compose setup does not provide one. This is a known limitation rather than a gap to close, and it is a deliberate consequence of choosing a webhook over a long-polling process.
