## Gotchas that will cost you time if you miss them

**Generated code.** `lib/api-zod` and `lib/api-client-react` are generated by
Orval from `lib/api-spec/openapi.yaml`. Never hand-edit them — your edits are
destroyed on the next codegen. Change the spec, then run codegen.

**The sum rule cannot live in the OpenAPI spec.** JSON Schema has no cross-field
constraints, so "these four amounts must total that fifth value" cannot be
expressed there. It runs as a separate validation step after the generated
schema parses, extending the hand-written balance validation the create and
update routes already perform.

**The architecture diagram.** If you touch any of `lib/db/src/schema/mahjong-sessions.ts`,
`lib/api-spec/openapi.yaml`, `artifacts/api-server/src/routes/index.ts`,
`artifacts/api-server/src/app.ts`, `artifacts/mahjong-scoreboard/src/App.tsx`
or `.replit`, you must also update `docs/architecture/runtime-architecture.source.json`
in the same change. Most of these tickets touch at least one. The HTML is
regenerated from that source by a local tool you may not have — if you cannot
regenerate it, update the JSON source anyway and say so in the PR.

**Do not add React component testing.** This repo has none, deliberately. Do not
introduce a testing library or DOM environment. The session form's tally,
lock/unlock flow and player picker are verified manually. All automated coverage
goes through the existing HTTP seam in the API server tests, which boots the real
Express app and mocks only the database and auth.

**Verify production data before any migration.** The spec states every existing
session already sums to the customary base and that no data repair is needed.
Re-confirm rather than trusting it — this query must return zero rows:

    SELECT s.id, s.played_on, b.sum_endings
    FROM mahjong_sessions s
    CROSS JOIN LATERAL (
      SELECT coalesce(sum((balance ->> 'endingAmount')::numeric), 0) AS sum_endings,
             count(*) AS player_count
      FROM jsonb_array_elements(s.player_balances) AS p(balance)
    ) b
    WHERE round(b.sum_endings, 2) <> 2000 OR b.player_count <> 4;

If it returns rows, stop and report rather than migrating.

**Expand–migrate–contract.** Tickets #12 → #13/#14 → #16 deliberately keep the
old `name` field on balances alive until #16 proves nothing reads it. Do not
shortcut this by deleting the name early — the sequence exists so the build
stays green at every step. If #16 turns into a rewrite instead of a deletion,
that means #14 was not finished.

**Never** push to main, force-push, or merge a PR yourself.

Two things I deliberately put in there that aren't in the tickets: the frontier query, so Replit picks work in a valid order rather than by number, and the production-data re-check, because the spec's "no repair needed" claim was true when I verified it but shouldn't be trusted blindly at migration time.
